# 美术资产存放与复用规范

- 用途：设计决策
- 适用范围：本项目美术源文件、Unreal 美术资产、样品、FPS 地图归属及跨项目复用；当前按 FPSDemo 落地
- 状态：资产规范于 2026-10-12 用户确认，地图分类于 2026-10-13 用户确认；新增资产与地图按此执行，现有目录分批迁移，完成情况以迁移记录为准
- 最后更新：2026-10-13

## 1. 存放原则

以当前项目的制作和维护为优先。制作源文件保存在项目根的 `ArtSource/`，引擎使用的资产保存在 `Content/`。两者按“项目主题 → 类别 → 具体资产或套件”对应组织，不建立项目外的唯一源库，不以工业风等视觉风格作为全局第一层分类。

“MCP”不作为玩家可见品牌；现有工程名和 `FPSDemo` 技术路径不因本规范自动重命名。美术风格仍以 [统一设计决策](DesignDecisions.md) 为准。

```text
ArtSource/FPSDemo/
  Weapons/M4/
  Characters/Operator/
  Environment/IndustrialKit/
  UI/IndustrialTerminal/
  Shared/
  Samples/Weapons/M4/
  Samples/UI/FontComparisons/

Content/FPSDemo/Art/
  Weapons/M4/
  Characters/Operator/
  Environment/IndustrialKit/
  UI/
  Shared/
```

这是目标结构，不表示这些目录全部已经存在。只建立实际需要的目录；具体资产名称和类别尽量对应，源目录和 Unreal 内部子目录不必逐字一致。当前入口及迁移批次见 [源文件整理记录](SourceOrganization.md)。

## 2. 每项资产的目录

按可独立复用的资产或套件集中保存，而非把全项目所有 Blender、FBX 和贴图分别混放。枪械通常一把一个目录；配套环境模块可以作为一个套件。已有多资产 Blender 库在拆分验证前仍由一个明确的套件目录持有，不复制为多个可编辑权威版本。

| 子目录或文件 | 内容 |
| --- | --- |
| `Source/` | 可编辑 Blender、绘画工程等制作源文件 |
| `Textures/` | 此资产专用的纹理、UI 图片；若同时保存原始贴图和烘焙结果，应进一步注明用途 |
| `Exports/` | FBX 等交换格式；由源文件导出，不作为另一份独立编辑来源 |
| `Previews/` | 实际渲染、截图和对照图，注明 Blender 预览或 Unreal 实机 |
| `Scripts/` | 仅服务该资产的生成、渲染、导出和检查脚本；跨资产工具继续放 `Tools/` |
| `Revisions/` | 重要评审节点的完整快照，不为每次小改动复制一整套 |
| `README.md` | 当前制作方式、状态、入口、共用依赖、Unreal 对应路径、重建方法及限制 |

资产 README 是随资产交接的入口，详细设计和实施证据仍放在 `Docs/`，通过相对链接关联。生成清单记录生成器、版本及校验信息；只能由权威来源或生成器更新，不能手改数据伪造验证结果。

## 3. 样品、正式资产与游戏接入

未验收样品放在 `Samples/<类别>/<资产>/`，内部遵循相同规则。样品可保存、渲染和独立复用；未要求 Unreal 预览时不必为它创建 `.uasset`。

样品转正需要明确的质量确认，转正后移到对应类别的正式目录，并同步修复引用。目录名称只表示管理状态，不代替验证。**视觉验收、进入正式目录、游戏接入是不同状态**，应分别记录。

当前精细 M4 仍为未实装样品；不能因源目录整理而替换正在使用的枪械。比较用字体和历史截图也不因迁入 Samples 而重新成为正式字体候选。

## 4. 专属资源与共用资源

专属贴图、材质和预览跟随具体资产。被多个资产实际共用的资源集中在 `Shared/`，例如字体及许可、公共材质源文件；不要为了“可能复用”提前把所有内容放进 Shared。

共用资源只有一个当前维护位置，资产 README 记录其依赖。样品快照中的历史副本可以保留，但必须明确是历史版本，不能与当前共用资源同时维护。字体和外部素材的来源、许可应随对应资源保存和交接。

Unreal 的模型、贴图、材质、UI 布局和主题归美术目录；伤害配置、开火逻辑等归对应玩法系统，通过引用使用美术。UI 中现有的项目代码依赖要如实记录，不能仅通过移动文件夹就宣称可独立迁移。

### 4.1 FPS 地图分类与归属

地图按用途分类、按归属保存。新增地图采用下表路径，每张地图或实验主题建立自己的子目录；只建立实际需要的目录。

| 分类 | 用途 | 存放位置 |
| --- | --- | --- |
| A：正式玩法 | 计划提供给玩家的对战地图、靶场和训练地图 | `Content/FPSDemo/Maps/Gameplay/<地图名>/` |
| B：玩法实验 | 验证移动、射击、AI、网络或关卡布局的独立实验场 | `Content/FPSDemo/Maps/Experiments/<实验主题>/` |
| C：综合美术展示 | 整场景的灯光、氛围、构图和综合美术展示 | `Content/FPSDemo/Maps/Showcases/<场景名>/` |
| C：资产或套件预览 | 单项资产或单个套件的检查与展示 | `Content/FPSDemo/Art/<类别>/<资产或套件>/Maps/` |

分类依据是用途，不是完成度。已经确定要作为正式可玩地图的白盒直接归 A；为回答某个设计或技术问题搭建的独立实验场归 B。位于 `Gameplay/` 不表示地图已验收或已接入大厅。

综合美术展示归 `Maps/Showcases/`；单项资产或套件的预览跟随对应资产，便于一起维护和复用。地图使用的共用模型、材质继续归 `Art/` 下对应资产或套件，由地图引用，避免每张地图复制一套。

以下为目标结构示例，不表示现有地图已经迁移：

```text
Content/FPSDemo/
  Maps/
    Gameplay/
      Foundry/LV_FPSFoundry.umap
      Training/LV_FPSTraining.umap
    Experiments/
      Movement/LV_TestMovement.umap
      ArenaLayout/LV_TestArenaLayout.umap
    Showcases/
      Industrial/LV_IndustrialShowcase.umap
  Art/
    Environment/
      AmmoSupplyCrate/
        Maps/LV_AmmoSupplyCratePreview.umap
```

本次仅确认新增地图的存放规则，未迁移现有地图。既有竞技场和靶场仍直接位于 `Content/FPSDemo/Maps/`，工业展示图仍位于 `Content/FPSDemo/Art/Industrial/Maps/`；现有地图制作背景见 [地图制作记录](../../FPSMaps.md)。后续迁移按第 7 节通过编辑器维护引用并验证，不能把示例路径当作当前入口。

## 5. 权威来源与历史版本

每项资产在 README 中明确当前制作方式：

- **程序生成阶段**：脚本及其输入是权威来源，修改应落到生成器或输入，再重新导出。
- **手工精修阶段**：Blender 或其他制作工程为权威来源；记录转换时间和入口。旧生成器只能输出到独立位置，不能覆盖精修源文件。

不允许两份文件同时被当作同一资产的当前版本。导出 FBX 不是另一条编辑分支。当前文件使用稳定名称和路径，阶段版本写入清单及 `Revisions/`；初版、比例确认、准备接入等重要节点可保存完整快照。

现有历史版本先保留，删除或清理另行决定。迁移目录不等于更新历史验证日期；历史报告中的旧绝对路径作为当时证据保留，通过迁移映射解释，当前操作入口必须指向新路径。

## 6. 跨项目复用

已经导入 Unreal 的资源，使用内容浏览器的 **Asset Actions → Migrate**，检查依赖清单后选择目标项目的 **Content 根目录**。Migrate 复制资产及其相关引用和依赖，例如材质需要的贴图；不要任意去掉必需依赖。[Epic 官方迁移说明](https://dev.epicgames.com/documentation/unreal-engine/migrating-assets-in-unreal-engine?application_version=5.8)

若还需要继续制作，另外携带该资产的源目录、必要的 Shared 源资源、README、生成清单和许可。Blender、制作脚本等不因 Unreal 资产迁移而自动成为新项目的源文件。

目标项目得到的是独立副本，之后不会自动同步修改。交接时记录使用的版本；再次更新前检查目标项目是否已有自身修改和同名资源。包含 UI、角色或玩法蓝图时，还需检查代码、插件、配置、骨骼等依赖，并在目标项目打开和实际使用验证；仅迁移成功不代表完整功能已接入。

## 7. 现有资产整理流程

第一阶段分批整理 ArtSource，第二阶段通过 Unreal 编辑器整理 Content。每批先建立旧路径到新路径的清单，核对文件和目标位置，再移动并同步维护脚本、代码中的制作路径、文档及索引。

移动源文件后检查字节完整性、生成器输入输出路径和必要的重新打开/导出行为。源文件修改涉及编辑器代码入口时，执行相称的编译检查。历史生成报告不手工改写为新验证结果。

第二阶段处理 `.uasset`、`.umap` 的移动、引用和重导入源路径，必须使用适用的编辑器工具；不通过文本补丁或资源管理器搬运来替代引擎引用维护。实际接入验证按影响范围执行，涉及网络或 GAS 时还要检查服务器与客户端。

当前迁移进度见 [源文件整理记录](SourceOrganization.md) 和 [美术待办](Tasks.md)。返回 [统一美术索引](README.md)。
