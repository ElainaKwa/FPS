# 文档分类与维护规则

- 用途：设计决策（文档治理规则）
- 适用范围：本项目 `Docs/` 内的文档、索引和配套资源
- 状态：已确认；分类与维护规则生效，旧文件实体迁移另行执行
- 最后更新：2026-09-30

本规则来自用户确认的文档分类讨论 Q1–Q7。创建新文档时遵循本规则；现有路径和历史标识集中迁移，不因本规则发布立即批量改名或搬动文件。

## 1. 目录先按主题，再按用途

采用实体目录分类，不能长期只依赖总索引给根目录中的大量文件分类。

- 第一层按 Demo 或项目主题划分，例如 `FPS/`、`Teaching/`、`KnowledgeLock/`。
- 主题内按系统聚合，例如 `FPS/Weapons/`、`FPS/Maps/`。同一系统的设计、实施和评审应在相邻位置，不散落到全项目的 Design、Reviews 等大目录。
- 一个主题文档较少时直接存放；内容增多、查找困难或存在多份同用途记录时，再按用途分目录，不预建大量空文件夹。
- 迁移完成后，`Docs/` 根目录只保留总索引 `README.md` 和本规则文件，其他文档及资源进入对应主题。
- 项目管理或跨系统资料按其实际主题归类，不强行塞入某个 Demo。

下面仅示意目标结构，不表示这些目录现在已创建，也不要求每个主题都拥有全部子目录：

```text
Docs/
  README.md
  DocumentationRules.md
  FPS/
    README.md
    Weapons/
      README.md
      DesignDecisions.md
      Usage.md
      Tasks.md
      FutureIdeas.md
      Implementation/
      Reviews/
      Generated/
      Archive/
      Images/
    Maps/
  Teaching/
  KnowledgeLock/
  ProjectMaintenance/
```

配图及附件跟随所属主题存放；多文档共享资源由一个明确目录持有，通过链接引用，不复制多份。移动主题目录时同时处理资源引用。

## 2. 七种固定文档用途

每份文档明确一个主要用途。相关内容可以简述并链接，不重复维护另一份权威正文。

| 用途 | 回答的问题 | 应包含 | 不应混入 |
| --- | --- | --- | --- |
| 设计决策 | 应该怎样做，为什么 | 已确认目标、规则、边界、取舍和决策依据；草案明确标识 | 将未经确认的评审建议当成最终需求 |
| 当前使用说明 | 现在如何使用或维护 | 与当前版本相符的操作、配置、入口及限制 | 将历史操作与当前操作无标识地混写 |
| 实施与验证记录 | 当时做了什么，如何验证 | 实施范围、版本、改动、证据、未验证项 | 将一次测试通过等同于全面验收 |
| 评审 | 发现了什么问题，建议如何改 | 事实、证据方式、影响、优先级、建议、未知项 | 未经验证的猜测写成已复现故障，或自动扩大范围 |
| 任务清单 | 接下来做什么，完成到哪里 | 明确待办、依赖、验收条件、完成证据链接 | 没有结果证据就勾选完成 |
| 未来想法 | 什么值得以后探讨 | 动机、已讨论边界、尚未决定内容 | 自动变成当前承诺或空实现 |
| 自动生成资料 | 当前源数据是什么 | 来源、生成入口、生成版本或日期、禁止手工维护说明 | 独立可编辑的第二份配置 |

总索引、主题索引和目录说明是导航文件，不必为符合七类而伪装成实施记录。

评审问题经确认纳入工作后，在任务清单引用原评审；涉及改变既定规则时，先更新设计决策。未来想法正式进入范围后标明承接文档，避免两处独立维护同一决定。

## 3. 文首标识与状态

每份正文文档在标题后至少注明：**用途、适用范围、状态、最后更新日期**。使用简短文本或列表即可，不强制 YAML 或复杂模板。

```text
# 文档标题

- 用途：评审
- 适用范围：FPS / Weapons，指定代码版本
- 状态：待处理建议；未修改代码
- 最后更新：YYYY-MM-DD
```

状态描述文档实际含义，不以含糊的“最终版”替代：

- 设计决策标明草案、已确认或已被替代。
- 使用说明标明当前适用版本或历史范围。
- 实施记录标明实施范围与验证边界，如“实现完成，双端待验收”，不能只写“完成”。
- 评审标明证据方式，如纯代码阅读、历史日志复核或实际运行；未执行的检查明确说明。
- 任务清单逐项记录完成度，未满足全部条件的条目保持待办或拆分。
- 未来想法标明未纳入当前范围。
- 生成资料的标识由生成器输出，不能为补模板手工编辑生成结果。

实施记录额外注明相关提交、构建号或其他可定位版本及证据入口。归档文档额外注明原因、归档日期和替代入口；如果没有替代文档，明确写“无替代文档”并说明原因。

最后更新日期对应本次实质修改，不把旧测试日期改成文档整理日期。历史结果与今天的状态分开标注。

## 4. 文件与目录命名

- 路径使用英文或现有代码标识符，正文标题使用中文。
- 同目录保持一致风格，采用清晰名称，例如 `DesignDecisions.md`、`Usage.md`、`Tasks.md`、`Reviews/ArchitectureReview.md`。
- 主题已在目录中表达时，不重复堆叠 `FPSWeapon...` 等长前缀。
- 不使用 `Final`、`Latest`、`New` 或“最终最终版”等不表达用途的名称。
- 日期采用 `YYYY-MM-DD`，仅用于需要保留的独立时间快照，例如 `Archive/ArchitectureReview.2026-09-29.md`。持续更新的主文档不因每次更新而新建日期副本。
- 阶段文件名应体现所属工作线或依赖目录，避免把 Demo 美术制作“第三阶段”与枪械重构“第三阶段”混为一谈。
- 历史命名不立即批量修正，统一纳入单独迁移任务。

## 5. 索引和引用

- `Docs/README.md` 负责主题入口、常见阅读路径和文档规则链接。
- 主题索引负责本主题文档用途、状态和必要阅读顺序；子主题较多时分层导航，避免总索引重复维护所有细节。
- 每份新增或迁移文档必须能从总索引沿主题索引找到。更新索引与文件变更在同一任务内完成。
- 项目内文档和图片优先使用相对链接，避免依赖某台机器的绝对路径。
- 代码定位优先使用文件与符号名；引用行号时注意代码变化，不能只保留已经过期的行号。
- 设计、实现、评审互相链接，不通过复制整段正文保持同步。

## 6. 归档条件

只有明确被替代、废弃或停止维护的文档进入所属主题的 `Archive/`。完成时间早、阶段已经交付、文件较旧，都不是单独的归档理由。

- 已完成的实施与验证记录保留在主题内，作为可追溯证据。
- 仍有参考价值但只描述旧状态的资料标明“历史记录”和适用范围，不自动归档。
- 归档内容保留原始判断；错误被纠正时，通过归档说明与当前版本链接提醒，不能继续将旧文当成当前依据。
- 当前索引指向有效版本，归档索引保留追溯入口。
- 修正小笔误不必生成一份归档副本；整体替代且需要追溯时再归档。

## 7. 变更检查

普通文档变更不需要启动引擎、编译或运行游戏。根据实际修改检查：

- 新建或迁移后，主题索引与总入口可达。
- 相对链接、图片引用与必要锚点有效，路径大小写一致。
- 文档状态、版本、日期与关联文档不互相矛盾。
- 完成标记有对应依据；不把编译、局部测试、完整打包和压力验收互相代替。
- 内容无乱码、意外转义和明显格式破坏。
- 移动/重命名时，还要搜索代码、脚本、AGENTS.md、其他文档中的路径引用，更新受影响的输入和输出位置。

生成资料始终从权威来源重新导出：参数变化修改源资产/源数据；格式、路径或分类标识变化修改生成器，再生成。不能手工改生成结果，也不能仅为改变参数而强行维护生成器中的第二份初值。

如果迁移涉及生成工具，应验证相应工具路径；仅因整理 Markdown 不触发全量游戏验证。无法完成的检查在交付中说明。

## 8. 现有文件迁移边界

规则首次落地时只新增规则及总索引入口；随后补充了项目指令和检查脚本。**没有迁移现有主题文件，也没有修改生成器或游戏代码**。旧文件路径、中文文件名和缺失的文首标识属于过渡状态。

后续迁移任务需先建立“旧路径 → 新路径”清单，再按主题迁移、修复引用和索引、处理生成输出路径、补充状态标识并完成检查。保留已有内容、验收证据和无关用户改动，不以整理名义删除历史资料。

## 9. Agent 执行入口与自动检查

项目根 [AGENTS.md](../AGENTS.md) 要求涉及文档的 Agent 先阅读本规则，并在交付前运行：

```powershell
python Tools/CheckDocs.py
```

[检查脚本](../Tools/CheckDocs.py) 使用 Python 3 标准库，可从任意工作目录启动。检查 UTF-8、文首四项标识与日期格式、英文路径、无意义的独立命名词、新增根目录文档、Markdown 相对链接/图片目标及路径大小写、从总索引沿链接的可达性。失败返回非零退出码。

[过渡清单](../Tools/DocCheckBaseline.json) 按精确文件路径与具体规则记录历史欠账，不豁免整个目录，不豁免失效链接。新文件必须全部通过；修复或迁移历史文件后删除对应例外，失效例外也会报错。禁止为了让检查变绿而增加或扩大豁免。历史元数据缺项在单独迁移任务中补齐；生成文件的缺项通过生成器修复。

脚本支持常见内联 Markdown 链接、图片及引用式链接定义，忽略代码块与行内代码。外部网址可用性、HTML 链接、锚点、未定义的引用式链接、附件分类、命名语义、状态与证据一致性仍需人工核对；它不完整解析所有 Markdown 方言。索引可达性检查包括正文链接，不验证导航是否易用。

修改检查器后运行其隔离测试：

```powershell
python -m unittest discover -s Tools -p test_check_docs.py
```

目前落实的是项目指令与本地检查，尚未配置远端 CI、合并门禁或 Git 提交钩子。它们不能技术性阻止跳过检查的提交，也不能保证所有工具读取 AGENTS.md。交接给其他工具时显式要求读取项目指令；对已经进行中的聊天，应提醒重新读取。需要强制阻止不合规变更合并时，再把同一检查命令接入实际托管平台的必需检查。
